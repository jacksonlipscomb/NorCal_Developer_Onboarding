# NorCal Developer Onboarding

A lightweight internal web app showing new NorCal developers step-by-step onboarding
instructions. Steps can be added and soft-deleted (records are preserved, not
hard-deleted), and each visitor can check off their own progress (stored locally in the
browser). Editing remains available on the API (`PATCH /api/steps/:id`) but has no UI.

## Architecture (three layers)

- **Frontend** — Vite + React 19 SPA (TanStack Query v5, Tailwind v4, Radix UI). Talks
  only to the edge API; it never holds Supabase credentials.
- **Middle tier** — Cloudflare Pages Functions in [`functions/api/`](functions/api), using
  the Supabase **service-role** key. These are the sole access path to the data.
- **Data tier** — Supabase Postgres. Table `onboarding_steps` with sequence-assigned
  ordering and a `deleted_at` soft-delete flag.

### Access model

There is **no app-level login**. The data boundary is the service-role key, used only
server-side. RLS is enabled with no policies and `anon`/`authenticated` are revoked, so the
public anon key reaches nothing. Because the mutation endpoints are otherwise open to anyone
who reaches the URL, the site is gated by **HTTP Basic Auth in a Pages Functions middleware**
([`functions/_middleware.ts`](functions/_middleware.ts)) — a shared `user:password` credential
stored as the encrypted `SITE_BASIC_AUTH` secret. The middleware runs on every request (page
and API) and **fails closed**: if the secret is unset, every request gets `401`. Cloudflare
Access (per-user email OTP) remains an optional future upgrade.

## API

| Method | Path             | Purpose                                             |
| ------ | ---------------- | --------------------------------------------------- |
| GET    | `/api/steps`     | List active steps, ordered                          |
| POST   | `/api/steps`     | Add a step (`{ title, body }`)                      |
| PATCH  | `/api/steps/:id` | Edit a step (`{ title?, body? }`) — API only, no UI |
| DELETE | `/api/steps/:id` | Soft-delete a step (sets `deleted_at`)              |

Unhandled methods return a structured `405` with an `Allow` header. Every response the app
produces (2xx/4xx) carries an `x-request-id` header, and each request logs one structured
line. The exception is an unexpected `500`: those are platform-generated by Cloudflare after
an error propagates, so they do **not** carry `x-request-id` — but the structured log line
(which always runs) still records the request ID for correlation.

## Prerequisites

- Node 20+ and npm (npm is the authoritative package manager — no `bun.lockb`).
- A Supabase project (URL + service-role key).
- Cloudflare account with Wrangler (installed here as a dev dependency).
- Docker Desktop running — only needed to run the local Supabase stack and DB tests.

## Local development

1. Install dependencies:
   ```bash
   npm install
   ```
2. Provide the function secrets in a **gitignored** `.dev.vars` (copy the example):
   ```bash
   cp .dev.vars.example .dev.vars
   # then edit .dev.vars with your SUPABASE_URL and SUPABASE_SERVICE_ROLE_KEY
   ```
3. (Optional) Run the data tier locally:
   ```bash
   npm run db:start     # supabase start (Docker)
   npm run db:reset     # applies migrations + seed.sql
   ```
4. Build the SPA and serve it together with the edge functions:
   ```bash
   npm run pages:dev    # vite build && wrangler pages dev dist
   ```
   `wrangler pages dev` auto-loads `.dev.vars`. The SPA dev server alone (`npm run dev`)
   does **not** serve the functions — use `pages:dev` for end-to-end work.

## Quality gates

```bash
npm run typecheck    # tsc -b across app + functions
npm run lint         # eslint
npm test             # vitest — validation, respond/logging, auth, and check-off unit tests
npm run build        # tsc -b && vite build → dist/
```

### Database contract tests (requires Docker)

```bash
npm run db:reset     # or `npx supabase start` first
npx supabase test db # runs supabase/tests/*.sql (pgTAP)
```

[`supabase/tests/onboarding_steps_test.sql`](supabase/tests/onboarding_steps_test.sql)
asserts the RLS lock, `service_role`/`anon`/`authenticated` grants, the check/unique
constraints, and seed idempotency.

## Provisioning the data tier (remote)

```bash
npx supabase link --project-ref <ref>
npx supabase db push --include-seed   # applies migration 0001 + idempotent seed
```

Do **not** use `supabase db reset` against a linked remote DB — it is local-only and
destructive. The seed is idempotent (it only loads when the table is empty), so
`--include-seed` is safe to re-run.

## 4. Deploy

1. Build and deploy SPA + functions to Cloudflare Pages:
   ```bash
   npm run pages:deploy   # vite build && wrangler pages deploy dist --project-name norcal-onboarding
   ```
2. In the Cloudflare Pages project settings, add **three** encrypted environment variables
   (Production): `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and `SITE_BASIC_AUTH`.

### Required gate before sharing the URL — Basic Auth

The production URL **must not be shared** until the gate is live. The gate is the
[`functions/_middleware.ts`](functions/_middleware.ts) Basic Auth check, driven by the
`SITE_BASIC_AUTH` secret in `user:password` form (e.g. `norcal:a-strong-password`).

- Set `SITE_BASIC_AUTH` as an **encrypted** variable, then **redeploy** so the middleware
  picks it up.
- It gates the whole site (page + API). Visitors get a browser username/password prompt;
  the SPA's API calls reuse the credentials automatically.
- **Fail-closed:** if `SITE_BASIC_AUTH` is unset, every request returns `401` — the site can
  never accidentally ship open. (Verify by deploying before setting the secret: the site is
  locked.)
- Rotate by editing `SITE_BASIC_AUTH` and redeploying. Distribute the password out of band.

Optional future upgrade: Cloudflare Access (per-user email OTP / Google Workspace IdP) for
per-user identity. It requires a Zero Trust org; Basic Auth needs no extra account.

### Backups

Soft-delete preserves rows. At deploy time, select the project's Supabase backup mode (daily
backups, or PITR if the plan offers it) and record the restore runbook location. On the free
tier, add a periodic off-site `supabase db dump`.
